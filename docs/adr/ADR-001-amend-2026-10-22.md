# ADR-001 amendment (22 Oct 2026): platform-independent input hashes (scorecard schema v2)

- **Status:** ACCEPTED 22 Oct 2026 (Shyam, "ADR-001 amend ok", before P04a Part B was approved).
- **Amends:** ADR-001 §6 (Reproducibility). Every other part of ADR-001 is unchanged: mode, metrics, M1 + M2 shown together, DEV-only label, and the stability run.

## Why
- **The fault (KNOWN_CORRECTIONS #25):** the scorecard at 6ddea50 (schema 1) hashed the input files as they sit in the working tree. Those bytes depend on `core.autocrlf`, so the gold and lock hashes come out differently on Windows (CRLF) and Linux (LF).
- **What is not affected:** metrics and per_row reproduce exactly. Claude checked this on Linux.
- **What is wrong:** only the provenance fingerprints are platform-specific.

## Change
1. **Schema `efrecon-scorecard/2`.** For each input (gold, factors, requirements-lock), `inputs` stores:
   - `git_blob`: the output of `git rev-parse HEAD:<path>`;
   - `sha256`: the hash of the bytes of `git cat-file blob HEAD:<path>`, i.e. the committed content, which is LF and the same on every OS.
2. **A clean tree is still required.** That guarantees the working tree equals HEAD for every input.
3. **The schema-1 file `scorecard-2026-10-22-6ddea50.json` stays FROZEN and unchanged.** Its hashes can still be checked by converting the files to CRLF.
4. **A confirmation run** at the P04a code commit (schema 2) is written as a new dated file. **Expected result** (pre-registered): metrics, per_row and needs_llm_ids are identical to the 6ddea50 scorecard. P04a changes no decision code. Any difference → STOP and explain; never tune.
5. **Cross-platform check:** Claude re-runs the same commit on Linux, and every `inputs` field must match the Windows file exactly.

## Worst case and undo
- **Worst case:** a reader compares schema-1 and schema-2 hashes directly and thinks the inputs changed. Guard: the `schema` field differs, and README §5 says the inputs are unchanged.
- **Undo:** easy. Only how the hashes are computed changes.
